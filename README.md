# nvim config

Портативный конфиг Neovim: Python-разработка (LSP, ruff, venv), Telescope,
neo-tree, встроенный терминал, тема monokai-pro. Разворачивается на новой
машине (macOS / Linux-сервер) двумя командами.

## Структура

```
~/.config/nvim/
├── init.lua                  # точка входа: options -> keymaps -> lazy
├── lua/
│   ├── config/
│   │   ├── options.lua       # vim.opt (отступы, номера строк, ...)
│   │   ├── keymaps.lua       # общие маппинги, не завязанные на плагины
│   │   └── lazy.lua          # bootstrap lazy.nvim
│   └── plugins/               # каждый файл = один plugin spec для lazy.nvim
│       ├── colorscheme.lua   # monokai-pro
│       ├── telescope.lua
│       ├── neo-tree.lua
│       ├── toggleterm.lua
│       ├── treesitter.lua
│       ├── completion.lua    # blink.cmp
│       ├── lsp.lua           # mason + pyright + ruff + lua_ls
│       ├── formatting.lua    # conform.nvim (ruff format, stylua)
│       └── python.lua        # venv-selector.nvim
├── bootstrap.sh               # ставит зависимости ОС + первый headless sync
└── lazy-lock.json             # ⚠️ появится после первого запуска — коммить его!
```

Это НЕ форк репозиториев Sin-cy — тема и общая структура (init.lua →
config → plugins) вдохновлены ими, но плагин-менеджер и LSP-настройка
сделаны заново под стабильный Neovim, без завязки на nightly-only API.

## Быстрый старт на новой машине

```bash
git clone <URL-вашего-репозитория> ~/.config/nvim
~/.config/nvim/bootstrap.sh
```

`bootstrap.sh` сам:
- ставит Neovim, git, ripgrep, fd, компилятор — через brew на macOS,
  через apt + официальный бинарник Neovim на Linux;
- прогоняет `nvim --headless "+Lazy! sync" +qa`, чтобы скачать все
  плагины без открытия UI (важно для серверов без графики);
- ставит LSP/tool-бинарники через mason.

После этого просто `nvim`.

## Почему lazy.nvim, а не `vim.pack`

В обоих репозиториях Sin-cy (`nvim-nightly` и `dotfiles`) используется
`vim.pack` — встроенный в Neovim менеджер пакетов — и `vim._core.ui2`,
экспериментальный UI-модуль. Оба доступны **только в nightly-сборках**
Neovim, API нестабилен и может измениться. Отсюда и название репозитория.

Для требования «разворачивается в одну-две команды на маке и на серверах»
это плохой выбор: пришлось бы либо собирать Neovim из исходников на
каждом сервере, либо гнаться за nightly-релизами. **lazy.nvim** — плагин,
а не часть ядра, работает на любом Neovim ≥ 0.9, имеет `lazy-lock.json` —
файл с точными коммитами всех плагинов, который **надо коммитить в git**:
это гарантирует, что через полгода на новом сервере накатятся ровно те
же версии плагинов, что у вас сейчас, а не что-то отличное.

## Python: как собран стек и почему

| Задача | Инструмент | Зачем именно он |
|---|---|---|
| Типы, автодополнение, go-to-definition | **pyright** | Стандарт де-факто для Python LSP, быстрый, хорошо ладит с venv |
| Линтинг + форматирование | **ruff** | Один бинарник на Rust, заменяет flake8+isort+black+десятки плагинов, на порядок быстрее |
| Определение venv | **venv-selector.nvim** + настройки pyright | См. ниже |

**Почему pyright + ruff, а не всё через один сервер.** Ruff — отличный
линтер/форматтер, но не даёт полноценного type-checking и навигации
по коду того же уровня, что pyright (или альтернатива — `basedpyright`,
форк pyright с более честным open-source статусом; замена — одна строка
в `lsp.lua`, если захотите). Поэтому связка pyright (типы, hover, переходы)
+ ruff (диагностика стиля/ошибок + форматирование) — типичный
рекомендуемый сетап 2025-2026, оба сервера работают параллельно, в
`lsp.lua` явно отключён `hoverProvider` у ruff, чтобы не было двух
всплывающих окон документации при наведении.

**Определение venv/пакетов.** Тут две дополняющие друг друга вещи:
1. `pyright` в `lsp.lua` настроен на `autoSearchPaths = true` — если у
   вас в корне проекта есть `.venv`, pyright найдёт его сам, без единого
   действия с вашей стороны.
2. `venv-selector.nvim` (`<leader>cv`) — на случай, когда venv лежит не
   в `.venv` в корне (poetry, conda, pyenv, venv с нестандартным именем).
   Плагин ищет все окружения на диске через Telescope, при выборе сам
   перезапускает pyright и ruff с нужным интерпретатором и выставляет
   `$VIRTUAL_ENV` в терминалах, открытых из nvim (в т.ч. в toggleterm).

## Mason: что это и почему он, а не альтернативы

**Mason** — менеджер, который ставит LSP-серверы, линтеры и форматтеры
(pyright, ruff, stylua...) не через `brew`/`apt`, а в
`~/.local/share/nvim/mason/`, одинаково на любой ОС.

Разбор вариантов, чтобы было понятно, почему выбор пал на него:

- **Mason (выбран)** — плюсы: один и тот же `lsp.lua` работает
  identично на маке и на сервере, не нужно помнить «на маке brew install
  pyright, на сервере apt/pipx install pyright»; `ensure_installed` в
  `lsp.lua` — это и есть декларативный список версий для новой машины.
  Минус: свои копии бинарников (немного лишнего места на диске), плюс
  для очень редких LSP-серверов их иногда ещё нет в реестре mason.
- **Глобальная установка через `pipx`/`uv tool install ruff`** —
  плюс: тот же бинарник ruff можно переиспользовать в pre-commit/CI вне
  редактора. Минус: на каждой новой машине это отдельный шаг, который
  легко забыть, и версии в редакторе/CI могут разъехаться.
- **Nix / системные пакеты** — самый воспроизводимый вариант, но
  оправдан только если вы уже используете Nix для всего окружения;
  для «мак + случайные серверы» это избыточная сложность.

Для вашего случая (маки + серверы, минимум ручных шагов) mason — самый
понятный и предсказуемый вариант, отсюда и оставлен как основной; если
позже захотите более «сквозной» ruff (используемый и в CI, и в
редакторе) — можно поставить `ruff` глобально через `uv tool install ruff`
и просто убрать `"ruff"` из `ensure_installed` в `lsp.lua`, конфиг не
развалится.

## Плагины: что и зачем

| Плагин | Роль |
|---|---|
| **lazy.nvim** | менеджер плагинов, lockfile для воспроизводимости |
| **telescope.nvim** + `telescope-fzf-native` | нечёткий поиск файлов/текста/буферов; `fzf-native` — C-реализация сортировки, сильно быстрее чистого Lua на больших репо |
| **neo-tree.nvim** | классическое боковое дерево файлов |
| **toggleterm.nvim** | плавающий терминал по `<C-\>`, с сохранением истории/сессии |
| **treesitter** | точная подсветка синтаксиса и отступы (нужен и для python, и для конфигов) |
| **blink.cmp** | всплывающее меню автодополнения от LSP — без него LSP даёт только диагностику/hover, но не автокомплит-попап |
| **mason / mason-lspconfig / mason-tool-installer** | ставят pyright, ruff, stylua |
| **nvim-lspconfig** | готовые конфиги для подключения к LSP-серверам |
| **conform.nvim** | форматирование по `<leader>mp` и при сохранении (ruff для python, stylua для lua) |
| **venv-selector.nvim** | выбор виртуального окружения |
| **monokai-pro.nvim** | тема, `transparent_background = true` |

## Тема и прозрачность

`transparent_background = true` в `colorscheme.lua` только отключает
заливку фона **внутри nvim**. Саму прозрачность рисует терминал —
в Ghostty это `background-opacity = 0.85` (или сколько нравится) в
`~/.config/ghostty/config`. Без этой настройки в терминале
`transparent_background` в nvim ничего не даст (будет просто чёрный фон).

В `colorscheme.lua` стоит `filter = "spectrum"` — один из встроенных
фильтров monokai-pro.nvim с тёплой/оранжевой палитрой, похожей на
скриншот. Другие варианты на выбор: `classic | machine | octagon | pro
| ristretto`. Проще всего сравнить визуально:
`:lua require("monokai-pro").setup({filter="classic"}); vim.cmd.colorscheme("monokai-pro")`
и заменить `filter` в файле, если понравится другой.

## Основные команды/маппинги (leader = Space)

| Клавиши | Действие |
|---|---|
| `<leader>ff` / `<leader>fg` | Найти файл / grep по проекту |
| `<leader>fb` | Список открытых буферов |
| `<leader>e` | Переключить дерево файлов |
| `<C-\>` | Переключить плавающий терминал |
| `<leader>cv` | Выбрать python venv |
| `gd` / `gr` / `K` | Definition / references / hover |
| `<leader>rn` | Rename |
| `<leader>ca` | Code action |
| `<leader>d` | Диагностика текущей строки |
| `<leader>mp` | Форматировать буфер вручную |

## Развёртывание конфига поверх существующих dotfiles

Если у вас уже есть отдельный репозиторий dotfiles (как `Sin-cy/dotfiles`)
и вы используете GNU Stow — просто положите содержимое этой папки в
`dotfiles/nvim/.config/nvim/` и застоуйте как обычно
(`stow nvim` из корня dotfiles). `bootstrap.sh` в таком случае можно
вызывать из общего `install.sh` дотфайлов.

## Обновление на всех машинах разом

```bash
nvim --headless "+Lazy! sync" +qa   # обновить плагины по lazy-lock.json
git add lazy-lock.json && git commit -m "bump plugins" && git push
```
На других машинах — просто `git pull`, версии подтянутся автоматически
при следующем запуске (lazy.nvim сверяется с lockfile).
