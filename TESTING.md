# Тестирование

Как устроены тесты этого конфига, что нужно раннеру, какими командами
гонять и на что смотреть. CI сюда намеренно не входит — по договорённости
его добавляют отдельно.

## Подход

Конфиг — это набор Lua-модулей поверх Neovim, а не приложение с бизнес-
логикой, поэтому обычный unit-testing тут не совсем в тему. Вместо этого
тесты гоняют **настоящий Neovim в headless-режиме** против **настоящих
файлов-фикстур** и проверяют то же самое, что вы бы проверили руками:
подключился ли LSP, поймал ли ruff ошибку, форматируется ли буфер,
переключается ли дерево файлов и т.д. Это по сути автоматизация того
набора ручных проверок, которым конфиг гонялся всю дорогу при разработке
(включая пару реальных багов, которые эти самые проверки и поймали —
см. ниже).

**Фреймворк**: [plenary.nvim](https://github.com/nvim-lua/plenary.nvim),
busted-style (`describe`/`it`/`assert`). Он уже тянется как зависимость
telescope/neo-tree, отдельно ставить не нужно. Другие варианты
(`mini.test`, ручные ассерты в чистом Lua) рассматривались, но
plenary — самый распространённый и документированный вариант именно
для тестирования nvim-конфигов/плагинов.

### Важное ограничение: то, что нельзя проверить headless

Не все баги ловятся в headless-режиме. Пример из реальной практики этого
репозитория: краш в подсветке синтаксиса (`nvim-treesitter` master-ветка
на Neovim ≥ 0.12) проявлялся только через decoration provider при
**реальной перерисовке экрана** — в headless-режиме без прикреплённого UI
эти колбэки просто не вызываются, баг не воспроизводится никак. Если
что-то подобное чинится — тест на него добросовестно написать не выйдет,
только ручная проверка в реальном терминале. В таких местах в коде
оставлены комментарии.

## Настройка окружения (что нужно раннеру)

Тесты запускают **настоящую синхронизацию плагинов и установку LSP-тулов**
в изолированном окружении — это не мок, а честная сборка конфига с нуля
(то же самое, что делает `bootstrap.sh` на реальной машине). Раннеру
нужно:

| Что | Зачем | Как проверить |
|---|---|---|
| `nvim` ≥ 0.11 (стабильная сборка, не из старых apt/dnf репозиториев) | сам конфиг требует `vim.lsp.config`/`vim.lsp.enable` | `nvim --version` |
| `git` | клонирование плагинов lazy.nvim, `.git` фикстуры для gitsigns-теста | `git --version` |
| `curl`, `tar` | lazy.nvim качает плагины | — |
| C-компилятор (`cc`/`gcc`) | компиляция treesitter-парсеров | `cc --version` |
| `tree-sitter` CLI | то же самое — `nvim-treesitter` (main branch) компилирует парсеры через него, не напрямую через компилятор | `tree-sitter --version` |
| `node` + `npm` | mason ставит `pyright` (npm-пакет) | `node --version` |
| `python3` | сам объект тестирования — Python LSP | `python3 --version` |
| Сеть наружу (GitHub, PyPI через npm/pip, registry mason) | первый прогон качает всё с нуля | — |

Если раннер уже настроен через `bootstrap.sh` (например, это тот же
образ/машина, где живёт сам конфиг) — всё из таблицы уже есть, ничего
доустанавливать не надо, `make setup` отработает быстро (просто проверит,
что всё на месте).

Если раннер чистый (типичный CI-контейнер) — **сначала `bootstrap.sh`,
потом тесты**:
```bash
~/.config/nvim/bootstrap.sh   # ставит nvim/rg/fd/tree-sitter/node как бинарники
cd ~/.config/nvim
make test
```
(`bootstrap.sh` уже умеет ставить всё из таблицы выше без sudo, если
git/компилятор уже есть в образе — см. README.md.)

## Команды

```bash
make setup       # синхронизировать плагины, поставить mason-тулы, подготовить фикстуры (venv-заглушку, git-репозиторий)
make test        # setup (если нужно) + весь набор тестов
make test-only   # только тесты, без setup — быстрее для повторных прогонов при итерации
make clean       # снести изолированное тестовое окружение и сгенерированные фикстуры
```

Тесты живут в `tests/config/*_spec.lua`, фикстуры — в
`tests/fixtures/`. Изоляция: `make setup` подкладывает символическую
ссылку `$XDG_CONFIG_HOME → <этот репозиторий>` во временный домашний
каталог (`.test-home/`, в `.gitignore`), так что тесты гоняются на
чистом окружении и никак не трогают ваш реальный `~/.config/nvim` /
`~/.local/share/nvim`, даже если тесты запускаются прямо из рабочей
копии конфига.

## Структура тестов

| Файл | Что проверяет |
|---|---|
| `smoke_spec.lua` | конфиг стартует без ошибок, все плагины lazy.nvim реально на диске, парсеры и mason-тулы установлены |
| `lsp_spec.lua` | pyright + ruff подключаются, ruff ловит unused import, `gd` уходит в другой файл (базовый класс), `gr` находит наследников, авто-подхват `.venv/bin/python` |
| `treesitter_spec.lua` | подсветка активна, парсер класса не падает (регресс на баг с master-веткой) |
| `formatting_spec.lua` | ruff-форматирование чинит код в буфере, не трогая файл на диске |
| `autopairs_spec.lua` | скобки/кавычки закрываются и вкладываются правильно |
| `neotree_spec.lua` | `<leader>e` во всех трёх состояниях (закрыто / открыто-не-в-фокусе / в фокусе) |
| `autocmds_spec.lua` | автопереход `cwd` на корень проекта |
| `gitsigns_spec.lua` | определение текущей ветки в фикстур-репозитории |
| `colorscheme_spec.lua` | все установленные темы переключаются без ошибок, кастомные оверрайды (яркость/bold) не трогают акцентные цвета |
| `keymaps_spec.lua` | все хоткеи из KEYMAPS.md реально забинжены |

## Метрики: на что смотреть

Полноценного "% покрытия строк", как в `pytest-cov` для обычных
приложений, тут нет и не будет — для Lua-конфигов поверх Neovim такого
зрелого тула просто не существует, и городить его ради процента ради
процента не стоит. Смотреть стоит на другое:

1. **Pass/fail по файлам, а не только общий итог.** plenary печатает
   `Success: N / Failed: N / Errors: N` на каждый `*_spec.lua` —
   при добавлении CI разумно парсить это построчно (или включить
   JUnit-вывод plenary, `PlenaryBustedDirectory` его поддерживает через
   доп. опцию), чтобы сразу видеть, какая **область** отвалилась
   (LSP? форматирование? тема?), а не только факт "что-то красное".
2. **Время прогона `lsp_spec.lua` отдельно от остальных.** Это
   единственный по-настоящему медленный файл (реальный старт pyright +
   ruff, обычно 5-15 сек на тест) — если он вдруг начинает занимать
   заметно больше, это симптом деградации (например, pyright переиндексирует
   что-то лишнее) ещё до того, как тест формально упадёт по таймауту.
3. **Сам факт "тест упал из-за таймаута" vs "тест упал из-за assert".**
   Таймаут в LSP-тестах обычно значит "сервер не успел подняться/ответить"
   (окружение медленнее обычного, повысьте таймаут в `helpers.wait_for*`)
   — это не то же самое, что "сервер ответил не то, что ожидали"
   (настоящая регрессия в конфиге).
4. **Список пропущенных проверок (headless-limitations).** Если при
   правке чего-то, что раньше требовало ручной проверки в реальном UI
   (см. раздел про decoration providers выше), стоит вручную пройти это
   в реальном терминале перед мержем — тестовый прогон зелёным этого не
   гарантирует.

## Известные баги, которые эти тесты нашли при первом прогоне

Не выдумано ради демонстрации — оба всплыли при первом же честном
запуске полного набора, до того как тесты были подогнаны под
существующее поведение:

- **`gI` (go to implementation) не работает для Python.** pyright не
  заявляет `implementationProvider` в capabilities вообще — `lsp_spec.lua`
  это поймал, документация и комментарий в `lsp.lua` были исправлены
  (раньше `gI` был расписан как "главный инструмент для ООП-навигации",
  что для Python неправда).
- **`map.callback()` ≠ реальное нажатие клавиши.** Первый вызов
  `<leader>e` в свежем процессе не открывал дерево при вызове
  зарегистрированного `callback` напрямую (`vim.fn.maparg(...).callback()`)
  — у lazy.nvim обёртка для ленивой загрузки плагина рассчитана на
  диспетчеризацию через настоящее нажатие клавиши (`nvim_feedkeys`), а не
  на прямой Lua-вызов. Тест был переписан на `nvim_feedkeys`, что заодно
  сделало его куда более честной проверкой реального пользовательского
  сценария.
