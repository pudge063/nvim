# Поиск по файлам (Telescope)

Отдельный глубокий разбор поиска — хоткеи есть и в [KEYMAPS.md](KEYMAPS.md#файлы-и-поиск-telescope)

видны из таблицы: как на самом деле работает нечёткий поиск, чем

через `make` при установке, см. `lua/plugins/telescope.lua`) поверх
`ripgrep`/`fd`.

## Какой пикер для чего

| Ситуация | Пикер | Хоткей |
|---|---|---|
| Знаете (примерно) имя файла | `find_files` | `<leader>ff` |
| Файл может быть в `.venv`/`node_modules`/начинается с точки | `find_files` + `no_ignore` | `<leader>fF` |
| Ищете текст/переменную/строку по содержимому файлов | `live_grep` | `<leader>fg` |
| То же, но текст может быть внутри venv/build | `live_grep` + `no_ignore` | `<leader>fG` |
| Уже открывали файл, но закрыли | `oldfiles` | `<leader>fr` |
| Прыгнуть между открытыми буферами | `buffers` | `<leader>fb` |
| Найти метод/класс по имени **в этом файле** | `lsp_document_symbols` | `<leader>fs` |
| Найти метод/класс по имени **в проекте** | `lsp_dynamic_workspace_symbols` | `<leader>fS` |
| Обзор всех ошибок/warning | `diagnostics` | `<leader>fd` |
| Как работает команда/опция самого nvim | `help_tags` | `<leader>fh` |

## Хоткеи запуска

| Клавиши | Действие |
|---|---|
| `<leader>ff` | Найти файл по имени |
| `<leader>fF` | Найти файл, включая gitignored (venv, node_modules, ...) |
| `<leader>fg` | Найти текст по содержимому файлов (grep) |
| `<leader>fG` | То же, но включая gitignored |
| `<leader>fb` | Список открытых буферов |
| `<leader>fr` | Недавно открытые файлы |
| `<leader>fh` | Поиск по `:help` |
| `<leader>fd` | Список диагностик (ошибки/warning) |
| `<leader>fs` | Символы (классы/методы) текущего файла |
| `<leader>fS` | Символы (классы/методы) всего проекта |

## Хоткеи внутри пикера

Работают одинаково во всех пикерах, пока открыто окно Telescope:

| Клавиши | Действие |
|---|---|
| `<C-n>` / `<C-p>` или `↓` / `↑` | Следующий / предыдущий результат |
| `<CR>` | Открыть выбранное (или все выделенные — см. [мультивыбор](#мультивыбор-и-quickfix)) |
| `<C-x>` | Открыть в горизонтальном сплите |
| `<C-v>` | Открыть в вертикальном сплите |
| `<C-t>` | Открыть в новом табе |
| `<Tab>` | Отметить текущий элемент (мультивыбор), курсор идёт дальше |
| `<S-Tab>` | Отметить и уйти вверх |
| `<C-q>` | Отправить все (или выделенные) результаты в quickfix и закрыть Telescope |
| `<M-q>` | То же самое, но в loclist (локальный для окна, не для всей сессии) |
| `<C-u>` / `<C-d>` | Прокрутить окно предпросмотра вверх/вниз |
| `<C-c>` или `<Esc>` (в normal mode пикера) | Закрыть Telescope |
| `<Esc>` дважды, если курсор ещё в insert (в строке поиска) | Сначала выйти в normal mode пикера, потом закрыть |

## Что уже включено по умолчанию — важная тонкость

В `lua/plugins/telescope.lua` дефолты пикеров переопределены **до**
разницы между `ff`/`fF`:

- `find_files` уже смотрит **скрытые файлы** (`hidden = true`) без
  `<leader>fF` — дотфайлы (`.env`, `.gitignore` и т.п.) видны и в обычном
  `<leader>ff`.
- `live_grep` уже ищет по скрытым файлам (`--hidden` в
  `vimgrep_arguments`) и учитывает регистр по правилу `--smart-case`
  (см. ниже) без `<leader>fG`.

Из-за этого **разница `ff`↔`fF` и `fg`↔`fG` — это ТОЛЬКО gitignored**
(`.venv`, `node_modules`, `dist`, всё из `.gitignore`), не скрытые
файлы вообще: те уже везде включены. Единственное, что везде выключено
всегда — содержимое `.git/` (`file_ignore_patterns = { "%.git/" }`),
и это не переключается никаким хоткеем.

`--smart-case`: если в запросе нет ни одной заглавной буквы — поиск
регистронезависимый; как только появляется хоть одна заглавная — поиск
становится регистрозависимым автоматически, без отдельного флага.

## Нечёткий поиск (`find_files`, `buffers`, ...): синтаксис fzf

`find_files`, `buffers`, `oldfiles`, `help_tags`, символы — всё это
фильтруется через `telescope-fzf-native` **нечётко** (fuzzy): буквы
запроса не обязаны идти подряд, важен только порядок. Внутри этого
есть операторы, которые стоит знать:

| Синтаксис | Значит | Пример |
|---|---|---|
| `foo bar` (пробел) | И `foo`, И `bar` (в любом порядке вхождения) | `models user` — файлы, где встречаются оба фрагмента |
| `'foo` | Точное вхождение подстроки `foo` (не нечёткое) | `'test_user` — только буквально `test_user` подряд |
| `^foo` | Совпадение должно **начинаться** с `foo` | `^main` — файлы, начинающиеся на `main` |
| `foo$` | Совпадение должно **заканчиваться** на `foo` | `.py$` — только `.py`-файлы |
| `!foo` | **Исключить** совпадения с `foo` | `!test` — всё, кроме файлов с `test` в пути |
| `^foo$` | Точное совпадение целиком | `^__init__.py$` |

Операторы комбинируются через пробел: `'user !test .py$` — точная
подстрока `user`, без `test` в пути, обязательно `.py` в конце.

## `live_grep`: это НЕ нечёткий поиск, это regex ripgrep

Важная разница с предыдущим разделом: строка, которую вы печатаете в
`live_grep`, идёт **напрямую в `rg` как regex-паттерн** (это
`vimgrep_arguments` — реальный вызов ripgrep на каждое нажатие
клавиши), а не фильтруется нечётко после факта. Практические
последствия:

- `.` в запросе — это «любой символ» (regex), а не буквальная точка.
  Ищете `foo.bar` буквально — экранируйте: `foo\.bar`.
- Работают полноценные regex-конструкции ripgrep: `foo|bar`
  (альтернатива), `\bword\b` (границы слова), `^import` (начало
  строки), `TODO:.*fix` и т.п.
- Операторы fzf (`'`, `^`, `$`, `!`) из раздела выше **здесь не
  действуют** — это другой движок поиска, не сортировщик результатов.
- Раскладка запроса как обычно — `rg` ищет по строкам (results —
  список строк-совпадений), а не по файлам целиком.

## Мультивыбор и quickfix

Частый сценарий: нашли `live_grep`'ом десяток вхождений, хотите
открыть их все разом, а не по одному. `<Tab>` на каждой нужной строке
(отметится), затем `<CR>` откроет все отмеченные буферами сразу, либо
`<C-q>` отправит все (или только отмеченные, если есть) в quickfix-
список — дальше по нему можно ходить `:cnext`/`:cprev`, или прогнать
`:cdo` для батч-правки по всем найденным местам разом (см.
[EX-COMMANDS.md](EX-COMMANDS.md) — `:argdo`/`:bufdo`, тот же принцип).

## Символы (`lsp_document_symbols` / `lsp_dynamic_workspace_symbols`)

Это не текстовый поиск, а поиск по **дереву символов от LSP**
(pyright) — то есть находит классы/методы/функции как семантические
объекты, а не по совпадению текста. Из-за этого:

- Работает только там, где LSP реально подключён и проиндексировал
  файл (Python-проект с доступным `.venv`) — на файлах без LSP список
  будет пустым.
- `lsp_dynamic_workspace_symbols` (`<leader>fS`, весь проект) может
  давать неполный список сразу после открытия большого проекта — pyright
  индексирует асинхронно в фоне, через пару секунд список дополнится
  при повторном вызове.
- Не путать с `<leader>fg` по слову `class Foo` — grep найдёт только
  буквальные вхождения текста, символьный поиск найдёт `Foo` даже если
  определение отформатировано необычно или разбито на несколько строк.
